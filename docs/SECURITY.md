# Security and scope

- **Provenance.** Full Git commit pins and SHA-256 commitments bind the bytes. A common repository ties releases and notes to one GitHub namespace. Repository ownership must be checked independently against the publisher’s official domain. A valid decision does not prove that an arbitrary repository belongs to a claimed publisher or that a release is the newest or complete.
- **Parsing and bounds.** Only HTTPS raw GitHub JSON paths with a complete commit SHA are accepted. Distinct files must be in the same repository. Duplicate JSON keys, malformed schemas, oversized documents and digest mismatches cannot produce conclusive findings. The 16 KiB bound applies to accepted response bodies after retrieval by GenVM.
- **Model boundary.** Methodology and notes are untrusted strings embedded in a bounded evidence JSON object. The policy instructs the model to ignore embedded commands. Output must classify every changed field using a closed vocabulary. A disclosure classification requires an exact quotation locally. Validators agree on normalized classifications and deterministic differences, while quote boundaries may differ. Prompt injection and semantic misclassification remain possible. Inspect the pinned notes before relying on a contested decision.
- **Consensus and storage.** Disagreement can prevent a write from finalizing successfully. Evidence-validation errors and malformed model responses produce inconclusive records if agreed. An inconclusive attempt may be retried under the same evidence ID. An established verdict or deterministic no-field-change result is returned on replay. Audit IDs hash sorted compact JSON evidence. Decision hashes use the same encoding over the stored record before the decision hash is added.
- **Scope.** Values alone cannot establish a methodology change. Missing field definitions must be documented in a subsequent version. The MVP reports keyed-row and field-level differences within the submitted slice and cannot infer a cross-release join. It evaluates disclosure, not data accuracy or regulatory compliance.
- **Wallet and hosting.** The dashboard reads finalized state over Studionet RPC and never receives signing keys. Studio's built-in account signs inside Studio. The deployment account can use Studio's code-upgrade mechanism on this development network. Check the source-matched commit and live verification evidence when relying on a particular implementation.
